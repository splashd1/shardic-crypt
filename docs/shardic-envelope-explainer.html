shardic-envelope · a threshold custody ceremony

A secret, broken into shards, held by no one who could betray it alone.

shardic-envelope extends shardic-prime's threshold recovery scheme with real, independent trustees. A vault's encryption key is split with Shamir's Secret Sharing over GF(256) into five fragments; each fragment is delivered only to the one device cryptographically authorized to hold it. The party running the ceremony — the combiner — never once sees a bare codeword, before or after.

1 mandatory prime trustee + 4 pool trustees. Threshold: prime + 2 of 4 pool.

Phase 01

Formation

Every trustee generates a keypair on their own device and registers the public half with the combiner — before any vault exists, independent of which vault they'll eventually help recover. Only once all five are registered can a vault be created at all.

Vault creation runs two transformations at once: the plaintext is sealed under a random key, and that key is fragmented so no single copy of it survives anywhere.

DEK Shamir split · GF(256) 1 prime mask + 4 pool shares

Then, and only then, each of the five resulting codewords is individually wrapped to its trustee's registered public key — never printed, never written to disk in the clear. The instant every envelope exists, the plaintext codewords are securely overwritten and deleted.

Phase 02

Protected & Dormant

The vault is sealed. Every codeword has already been destroyed in plaintext form — what remains are five individually-wrapped envelopes and a ciphertext file that, on its own, decrypts for no one. This state has no expiry; it can sit untouched indefinitely.

Not the combiner, not the operator who ran the ceremony, not any one trustee acting alone — nobody holds enough of the secret to reconstruct the key by themselves. That's the point: custody is distributed by construction, not by policy.

No mapping is ever stored between a codeword and the share it unlocks. Recovery works by trial against every unmatched share, using AES-GCM's own authentication tag as the correctness check — so even the metadata sitting in a shared .krypt file can't be used to infer who holds what.

sealed · no expiry

Phase 03

Threshold-Proof

An operator opens a recovery session. Each live trustee decrypts its own envelope locally, on its own device, and derives its fragment of the key — then sends back only that fragment, never the codeword that produced it.

prime, live pool, live paused

Threshold is prime + 2-of-4 pool — three trustees, not five. dave and erin being offline changes nothing: alice, bob, and carol are enough.

The self-addressed envelope

The envelope a trustee unwraps to get its codeword also carries the combiner's own public key, bundled in alongside it. That's what lets the trustee wrap its reply shard back to the combiner without a separate lookup step — the return address rides along with the original delivery.

Phase 04

Finalize & Verify

Once the prime mask and enough pool shares have arrived, the combiner reconstructs the DEK via Shamir combination and decrypts the sealed ciphertext. The recovered output is then compared, byte for byte, against the original.

The proof isn't that the ceremony ran without errors — it's that the output is provably, bit-for-bit, the same file that went in.

Why the ceremony can be trusted

Trust properties

No single-party custody

Not the combiner, not the operator, not any one trustee — nobody holds enough of the secret alone, at any point in the lifecycle.

No stored mapping

Which codeword unlocks which share is never recorded. A stolen or leaked .krypt file reveals nothing about trustee-to-share assignment.

Codewords never travel

Each trustee unwraps and matches its own codeword locally. The combiner receives only the derived shard — never the codeword itself.

Threshold, not unanimity

Recovery needs prime + 2-of-4 pool, proven by pausing two trustees mid-ceremony and recovering anyway.

What the reference demo simplifies

The runnable version of this ceremony (Keycloak + a Flask combiner + five trustee containers) takes deliberate shortcuts for a local walkthrough. None of them are secret — naming them is part of the demo:

Trustee identity is confirmed via Direct Access Grant with a plaintext demo password, standing in for a real interactive OIDC flow.

The operator's admin actions are gated by a static shared-secret header, not a modeled Keycloak identity.

Keycloak runs in development mode with an embedded database, not a production topology.

There's no fingerprint cross-check of the combiner's own bundled public key against Keycloak.
